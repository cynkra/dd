# Proposal: one YAML source of truth for DuckDB function documentation

This file is a working note, companion to
[`duckdb-web-docs-review.md`](duckdb-web-docs-review.md)
(the drift catalog that motivates it) and
[`duckdb-argument-descriptions.md`](duckdb-argument-descriptions.md)
(per-argument descriptions, which the schema below accommodates).

The goal: a single, commented, reviewable source
from which both DuckDB's in-tree `functions.json` documentation
(base functions *and* the in-tree `core_functions` extension)
and duckdb-web's function pages are generated,
each through its own filter.
Constraints: maximum fidelity to today's outputs,
minimal (ideally empty) diffs at migration time,
and a review workflow where content changes are semantic diffs,
not formatting noise.
Content amendments are *noted*, never folded silently into the migration;
they land on the shared source afterwards.

## 1. Status quo: what is generated today, and from what

### 1.1 duckdb-web

Exactly five pages under `docs/{preview,current}/sql/functions/`
contain generated content, delimited by HTML comment markers
(`<!-- Start of section generated by scripts/generate_sql_function_docs.py; categories: [...] -->`):

| Page | Generated lines (current) | Categories |
|---|---|---|
| `array.md` | 15–90 | `array` |
| `blob.md` | 15–172 | `blob` |
| `lambda.md` | 46–92 | `lambda` |
| `list.md` | 12–820 | `list` |
| `text.md` | 19–858 | `string`, `regex` |

`scripts/generate_sql_function_docs.py` produces those sections by:

* querying `duckdb_functions()` of a **release-build binary**
  (not the JSON files), filtered by the page's categories;
* merging a hard-coded Python `OVERRIDES` list for entries the catalog
  cannot describe — table functions (`read_blob`, `read_text`),
  macros (`md5_number_lower/upper`), `unnest`,
  and the `list_*` aggregate macros;
* rewriting cross-references through an in-script URL table
  (`apply_url_conversions`), so prose stays engine-side
  and Jekyll `{% link %}` tags are added website-side;
* computing every example's **Result** row live,
  by executing `SELECT ⟨example⟩::VARCHAR` against the binary.

Everything *outside* the markers on those five pages
(intros, the `fmt`/regex syntax sections, slicing prose)
and **all other ~25 pages** (`aggregates`, `numeric`, `date`, `timestamp`,
`map`, `struct`, `union`, `utility`, `window_functions`, …) are manual —
which is where nearly every error in the review lives.

Two adjacent facts worth recording:

* `scripts/generate_function_json.py` is **defunct**:
  it globs `src/core_functions/**` (moved to `extension/core_functions`
  in DuckDB 1.2), writes `docs/functions.json`,
  which no longer exists in the repo and has no consumer.
  Delete it or revive it on the new source (§5).
* `docs/current/core_extensions/spatial/functions.md` has no in-repo
  generator; it is produced in the `duckdb-spatial` repository
  (from its C++ doc annotations) and copied over wholesale.
  Out of scope here, but the schema below does not preclude
  spatial adopting it later.

### 1.2 DuckDB

The `functions.json` files are the *hand-maintained source*
(64 files at current `main`):

* `src/function/{scalar,aggregate,window}/⟨category⟩/functions.json`
* `extension/core_functions/{scalar,aggregate}/⟨category⟩/functions.json`

`scripts/generate_functions.py` turns each file into a
`⟨category⟩_functions.hpp` header plus a `function_list.cpp` registration
(the "Do not edit" generated C++), embedding description, examples,
parameters and categories into `FunctionDescription` —
which is what `duckdb_functions()` serves,
and therefore what duckdb-web's generator and `dd` consume at one remove.

Schema today (4-space-indented JSON, a list of entries per file):
`name`, `parameters`, `description`, `example` *or* `examples`,
`categories`, `type`, `struct`, `aliases`, `variants`, `extra_functions`.
Two generations of the `parameters` field coexist:
the legacy comma-separated string (`"parameters": "string,index"`)
and the structured form already used in newer files
(`"parameters": [{"name": "string", "type": "VARCHAR"}, …]`,
e.g. `array_extract` in `src/function/scalar/list/functions.json`).
The migration to the structured form is underway upstream;
the YAML schema adopts it as the only form (§5, amendment A2).

### 1.3 dd

`dd` reads `duckdb_functions()` (all core extensions loaded, since dd#28)
and merges the same `functions.json` files for gaps, aliases and categories.
It needs no change for this proposal:
as long as `functions.json` continues to exist — generated instead of
hand-edited — `dd` keeps working unmodified,
and can later read the YAML directly for the extra fields.

## 2. The shared YAML source

One `functions.yaml` next to (eventually instead of) each `functions.json`,
same directory layout, same one-entry-per-function structure,
living in `duckdb/duckdb` — the repository both consumers already read
(duckdb-web's `generate_all_docs.sh` receives a DuckDB checkout as `$1`).

Why YAML rather than richer JSON:

* **comments** — provenance notes, review annotations,
  "checked against engine vX.Y" markers;
* **block scalars** — the ~260 website descriptions that are richer than
  the JSON one-liners can merge upstream without becoming
  unreadable single-line strings;
* **anchors** — shared sentence fragments
  (the "A set of optional `options` can be set." suffix family)
  defined once per file.

Schema: a strict superset of the JSON schema, structured parameters only,
plus an optional `web` block and per-argument descriptions:

```yaml
- name: regexp_extract_all
  struct: RegexpExtractAllFun
  type: scalar_function_set
  categories: [string, regex]
  variants:
    - parameters:
        - {name: string, type: VARCHAR}
        - {name: regex, type: VARCHAR}
        - {name: group, type: INTEGER, default: 0}      # A3
      description: >-
        Finds non-overlapping occurrences of `regex` in `string`
        and returns the corresponding values of `group`.
      example: regexp_extract_all('Peter: 33, Paul:14', '(\w+):\s*(\d+)', 2)
  web:                       # website-only; stripped by the JSON emitter
    page: text               # anchor page when categories span pages
    hide: false              # exclude from generated web sections
```

Website-only *entries* (today's Python `OVERRIDES`:
`read_blob`, `read_text`, `unnest`, `md5_number_*`, the `list_*` macros)
become ordinary YAML entries with `web.only: true` —
the JSON emitter skips them, so the engine build is untouched,
and the override list stops living in a website script.
Cross-references in descriptions stay in the neutral textual form
already used today ("see the `read_blob` guide");
the URL mapping table remains website-side.

## 3. Emitters and filters

```
functions.yaml ──(emit-json: strip web.*, down-convert)──▶ functions.json   (checked in)
      │                                                        │
      │                                       scripts/generate_functions.py (unchanged)
      │                                                        ▼
      │                                          C++ headers → binary → duckdb_functions()
      │                                                        │
      └──(emit-web: category filter, hide-list, ─────────▶ marker-delimited
          URL mapping, results run on binary)              sections in *.md
```

* **`emit-json`** (new, small): YAML → `functions.json`,
  4-space indent, each entry's key order preserved as-is
  (canonicalizing the order is deliberately *not* part of the migration —
  it would grow the diff and break clean replays; see A9),
  trailing newline — **byte-identical output for the migration commit**.
  `functions.json` stays checked in and `generate_functions.py`
  stays unchanged, so there is zero C++ or build-system churn;
  the JSON files merely gain a "generated from functions.yaml" header rule
  (enforced by CI, §3.1).
  Later, optionally, `generate_functions.py` learns to read YAML
  and the JSON files are dropped — a separate decision.
* **`emit-web`**: `generate_sql_function_docs.py` gains a YAML loader
  for descriptions, parameters, aliases, variants and categories,
  keeping the binary for what only the binary knows:
  overload resolution as-registered, and **live example results**.
  Its filters are the existing ones, now data- instead of code-driven:
  per-page category selection, `web.hide`, alias folding.
  A `--verify` mode regenerates and diffs, for CI on both repos.

Different consumers, different filters, one source:
the engine build wants everything except `web.*`;
the website wants per-page category slices minus hidden entries
plus `web.only` extras; `dd` wants everything including `web.*`-hidden
functions (it documents even the debug helpers, with its own filters);
a revived `generate_function_json.py` (search index) would be
one more ~20-line filter.

### 3.1 Fidelity and minimal-diff rules

1. **Bootstrap is mechanical**: `functions.json` → `functions.yaml`
   by script, then `emit-json` back, `cmp` byte-identical.
   The migration PR therefore shows: new YAML files,
   *zero* JSON changes, one CI job.
   Reviewing it means reviewing the converter, not 64 files.
2. Any transformation that would change JSON bytes
   (key reordering, `example` → `examples`, string → structured parameters)
   is deferred to a **noted amendment** (§5), each its own commit,
   reviewed with the semantic diff filter (§4) so the review shows
   only the intended semantic change.
3. `emit-web --verify` must reproduce the five current generated sections
   modulo already-known drift (the review's `list_intersect` case)
   before the website switches over.
4. Expanding generation to a manual page (§6) is accepted only when the
   generated section reproduces the current page content
   up to whitespace — differences are either fixed in YAML first
   (porting the page's better prose upstream) or flagged as
   review findings. One page per PR.

## 4. Reviewing JSON/YAML changes semantically

A Git diff filter that compares JSON semantically does exist,
in several forms; recommended setup, cheapest first:

* **`jq` textconv** (no new dependency; display-only, does not affect
  merges):

  ```
  # .gitattributes
  *.json diff=json
  # .git/config or ~/.gitconfig
  [diff "json"]
      textconv = jq --sort-keys .
  ```

  `git diff`/`git log -p` then compare normalized documents —
  key order and formatting noise disappear.
* **`jd`** (github.com/josephburnett/jd) is a JSON-native structural
  differ that ships an explicit **git diff-driver mode**:

  ```
  [diff "jd"]
      command = jd --git-diff-driver
  # .gitattributes
  *.json diff=jd
  ```

  Output is path-addressed (`@ ["list","0","description"]`) —
  ideal for reviewing amendment commits.
* **`dyff`** does the same for the YAML side
  (`dyff between`, with documented git `difftool` integration),
  and **difftastic** is a good general syntax-aware external diff
  (`GIT_EXTERNAL_DIFF=difft`) covering both formats.
* In CI, semantic equality is a one-liner —
  `diff <(jq -S . a.json) <(jq -S . b.json)` or `jd a.json b.json` —
  used by the §3.1 bootstrap check and the
  "JSON files match the YAML" guard.

## 5. Amendments to perform on the shared source (noted, not bundled)

Ordered; each is a separate, semantically-diffed change *after* migration:

* **A1** — normalize `example` / `examples` to a single list-valued
  `examples` field (byte-level JSON change, zero semantic change;
  consumers already handle both).
* **A2** — finish the structured-`parameters` migration everywhere
  (upstream is already part-way; unlocks per-argument descriptions,
  see `duckdb-argument-descriptions.md`).
* **A3** — record optional arguments and defaults structurally
  (`default:`), replacing the website's bracket notation heuristics
  (`bar(x, min, max[, width])`).
* **A4** — add the alias links the website knows and the metadata lacks:
  `geomean` ↔ `geometric_mean`, `wavg` ↔ `weighted_avg`,
  `list_append` ↔ `array_append`/`array_push_back`,
  `today` ↔ `current_date`, `dense_rank` ↔ `rank_dense`, ….
* **A5** — add entries for the website's `OVERRIDES`
  (`read_blob`, `read_text`, `unnest`, `md5_number_*`, `list_*` macros)
  with `web.only`/table-function typing, deleting the Python list.
* **A6** — fix the factual errors found in the review, on whichever side
  is wrong: `histogram*` → `MAP` (JSON wrong), `make_timestamp_ms`
  milliseconds (JSON wrong), `regr_sxx/sxy/syy` sums-of-deviations
  (both wrong differently), `hamming` typo (JSON), `count_if` boolean-only
  (web wrong), `map_extract` empty-list (web detail wrong), ….
* **A7** — port the ~260 richer website descriptions upstream
  as block scalars, page by page, in step with §6.
* **A9** — canonicalize per-entry key order
  (`name`, `parameters`, `description`, `examples`, `categories`,
  `variants`, `type`, `struct`, `aliases`, `extra_functions`),
  in YAML and JSON together.
  Optional: it buys uniformity, costs a one-off ~100-line
  semantically-empty diff, and is the one normalization that
  conflicts with replaying independent fixes — which is why the
  migration no longer performs it.
* **A10** — give the three `regr_s**` helper aggregates real examples.
  Their `example` fields hold defining formulas, not invocations
  (`regr_sxy`: `REGR_COUNT(y, x) * COVAR_POP(y, x)`;
  `regr_sxx`/`regr_syy`: `REGR_COUNT(y, x) * VAR_POP(x|y)`) —
  until the minimal-fixes branch, that formula was the *only*
  documentation of `regr_sxx`/`regr_syy` (their descriptions were empty),
  and paraphrasing it badly is how the wrong prose arose in the first
  place. Replace each example with a real call (`regr_sxy(y, x)`, …)
  and append the equivalence to the description
  ("Equivalent to `REGR_COUNT(y, x) * COVAR_POP(y, x)`.").
* **A8** — "can not" → "cannot" in the four array-distance/similarity
  descriptions ("The array elements can not be `NULL`",
  `extension/core_functions/scalar/array/functions.yaml`);
  the nonstandard spelling propagates from there to the generated
  `array.md` sections (12 of the website's 19 occurrences) and to `dd`.
  The ~186 remaining "can not" comments and error strings elsewhere in
  the DuckDB sources are an ordinary cleanup PR, outside this queue.

## 6. Rollout

1. `duckdb/duckdb` PR: converter + YAML files + `emit-json`
   + CI equality guard. Empty JSON diff.
2. `duckdb/duckdb-web` PR: `emit-web` reads YAML from the source checkout;
   regenerate the five sections; near-empty diff
   (surviving differences are review findings, listed in the PR).
3. Amendments A1–A6 as individual PRs on the YAML.
4. Page-by-page expansion of generated coverage,
   `aggregates.md` first (largest drift surface in the review),
   then the date/time family; each page's manual prose that is *better*
   than the metadata moves upstream via A7 in the same PR,
   under the §3.1(4) reproduction rule.
5. `dd` follows for free via `functions.json`,
   and switches to reading `functions.yaml` directly
   when the extra fields (per-argument docs, `web` hints for
   pkgdown grouping) become worth it.

## 7. Open questions

* Should `generate_functions.py` eventually read YAML directly
  and the JSON files disappear, or is generated-JSON-forever acceptable?
  (Python in the build already depends on nothing beyond stdlib;
  PyYAML would be a new build dependency — `emit-json` avoids
  that question for now.)
* Window functions: `src/function/window/*/functions.json` exists,
  but the website's `window_functions.md` prose
  (frame semantics, `ORDER BY` in aggregates) is structural,
  not per-function — that page likely stays majority-manual
  with a generated function-list section only.
* The `duckdb-spatial` repository generates its function reference from
  C++ annotations; converging it on the same YAML schema would unify the
  last big function surface, but is a separate conversation.

## 8. Implementation (prototype, on the review branches)

The design above is implemented end to end on branch
`claude/duckdb-docs-review-d86823` of `krlmlr/duckdb` and
`krlmlr/duckdb-web`, relaxing byte-identity per review feedback:
the JSON artifact is *normalized* rather than byte-preserved
("similar in spirit"), and reading YAML directly from
`generate_functions.py`, as well as duckdb-spatial, stay out of scope.

`krlmlr/duckdb` (four commits, reviewable independently):

1. `scripts/functions_yaml.py` (~170 lines, PyYAML only) with three
   subcommands:
   `to-yaml` (one-time bootstrap conversion),
   `to-json` (emit the normalized `functions.json` artifact),
   `check` (CI guard: JSON semantically matches YAML).
   The YAML holds the normalized form (`examples` always a list);
   the JSON emitter maps back to the files' established conventions,
   so `example` → `examples` unification stays queued as amendment A1.
   `check` fails on any semantic delta, and unknown keys are a hard error.
2. Bootstrap: 38 `functions.yaml` files converted from the JSON
   (449 entries; structured variant parameters render as
   `{name: x, type: T}` flow mappings, descriptions as folded scalars).
3. Regenerated `functions.json`.
   The emitter reproduces the files' established conventions —
   inline scalar lists and parameter objects, singular `example`,
   and (after review feedback) **per-entry key order preserved** —
   so **22 of 38 files are byte-identical**
   and the rest shrink to +268/−434 lines
   (down from +2876/−1170 in a first, naive `json.dumps` version:
   the bulk really was indentation and layout,
   and another slice was key-order canonicalization, now dropped).
   What remains normalizes genuine defects and per-file deviations:
   stray blank lines, misindented lines, one tab-indented file,
   one 2-space file, unicode escapes vs. UTF-8,
   and multiline scalar lists.
   Under the configured diff driver the commit is **semantically empty**.
   Verified: `scripts/generate_functions.py` output — the generated C++ —
   is byte-identical before and after.

Both branches are rooted directly on upstream `main`
(the fork's unrelated infrastructure commits are no longer in their
history), and a third, **super-minimal branch**
`claude/functions-json-minimal-d86823` (`main` + 2 commits)
carries only what is unarguably wrong:

* *Fix stray whitespace*: blank lines between and after entries
  (enum, the three window files), a 5-space and a tab-indented closing
  brace (math), 6-space entries in the 4-space struct and sequence
  files, and a misindented key line in window/value —
  +18/−34 across 7 files, no content changes.
  Internally *consistent* per-file styles (the tab-indented variant
  file, the 2-space geometry file) are deliberately left to the
  discretionary migration.
* *Fix and add descriptions in the regression aggregates and hamming*:
  the `hamming` typo, the wrong `regr_sxy` description,
  and new descriptions for `regr_sxx` / `regr_syy`
  (previously empty — the defining formula in their `example` field
  was their only documentation; see A10),
  with their regenerated headers.

Verified by replaying: rebasing the full five-commit series onto the
minimal branch completes **without conflicts** and produces a tree
**byte-identical** to the full branch's tip —
the minimal branch is a strict, mergeable subset.
(An earlier canonical-key-order emitter failed exactly this test:
reordering `aliases`/`type` next to a stray blank line in
`window/ranking` collided with the whitespace fix —
the empirical reason key order stays untouched.)
4. A demo amendment editing only YAML and regenerating JSON:
   the `hamming` "between to strings" typo
   and the wrong `regr_sxy` description (§ review, section 4).
   The regenerated C++ headers ride along in the same commit,
   showing the full YAML → JSON → codegen propagation.

`krlmlr/duckdb-web` (one commit):

* `scripts/generate_sql_function_docs_from_yaml.py` imports the existing
  generator and swaps only its data source:
  `DocFunction` records are built from the checkout's `functions.yaml`
  (variants × categories, alias rows synthesized from `aliases`)
  instead of `duckdb_functions()`;
  rendering, `OVERRIDES`, sorting, pruning and URL conversion
  are reused unchanged, and example results are still executed live.
  A tolerant fallback emits result-less example rows when the installed
  engine predates a function (metadata newer than engine).
  Note: the upstream generator requires Python ≥ 3.12 (PEP 701 f-strings).
* All five generated sections regenerate with 2 warnings and a
  +177/−147 diff across the five pages, which decomposes into:
  genuine metadata evolution (`overlay` is new upstream, next to the
  1.5.5 engine used for results); one rendering *fix*
  (`array_resize(list, size[[, value]])` → `[, value]`);
  and optional-argument renderings that need amendment A3
  (`default:` in YAML) to match the catalog's overload-derived brackets
  (`list_sort(list[, col1][, col2])` currently regenerates as
  `list_sort(list)` because the single YAML variant lists no optionals).
  That last class is the main fidelity gap of the prototype
  and A3 is the fix, not more override code.

## 9. Diff filters: observed behavior

Tools exercised on the commits above
(jd 2.5.0 via `go install github.com/josephburnett/jd/v2/jd@latest`,
difftastic 0.69.0 via `cargo install difftastic`,
dyff via `go install github.com/homeport/dyff/cmd/dyff@latest`,
plus stock `git` + `jq`).
All outputs below are captured verbatim, uncolored.
Summary first:

| Filter | Setup | Bulk-regen noise | Path-addressed | Word diff inside strings |
|---|---|---|---|---|
| plain `git diff` | none | high (reorder shows as churn) | no | YAML source: yes, via `--word-diff`; JSON: line-level |
| `jq` textconv | 2 config lines | hidden | no (line numbers) | **yes** (`--word-diff` composes with textconv) |
| `jd` diff driver | go install + 2 lines | minimal, exact paths (`@ [1,"variants",0,"example"]`) | **yes** | no (whole-value − / +) |
| difftastic | cargo install, `GIT_EXTERNAL_DIFF` | low (syntax-aware) | no (aligned lines) | in color terminals: sub-line token highlight (lost in plain capture) |
| `dyff` (YAML) | go install, difftool | n/a (YAML side) | **yes**, human labels (`regr_sxy.description`) | no (− / + values) |

Two observations that shape the choice:

* Because `functions.json` becomes a *generated, canonical* artifact,
  its plain diffs are already mostly clean after the migration;
  the semantic filter earns its keep on the one-time normalization
  review, on guarding hand-edits, and on word-level readability
  of long description strings.
* On the YAML source files, plain `git diff --word-diff`
  is already excellent (case 2b below) —
  "no new tools" is a defensible choice for day-to-day review,
  with `jd`/`dyff` reserved for CI equality checks.

**Decision**: standardized on the `jq` textconv driver —
zero new dependencies, reorder/reformat noise hidden,
and `git diff --word-diff` gives word-level diffs inside JSON strings
(the only option that does).
`.gitattributes` on the `krlmlr/duckdb` branch binds
`src/function/**/functions.json` and
`extension/core_functions/**/functions.json` to the driver;
each user enables it once with
`git config diff.functionsjson.textconv 'jq --sort-keys .'`.
`jd` remains the CI equality check
(`functions_yaml.py check` already covers YAML↔JSON).

Configuration used for the captures (repo `.gitattributes` + user config):

```
# .gitattributes
*functions.json diff=semantic
# user config, option A (jq):
[diff "semantic"]
    textconv = jq --sort-keys .
# user config, option B (jd):
[diff "semantic"]
    command = jd -git-diff-driver
```
