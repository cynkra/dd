# Review: duckdb.org function docs vs. `dd` and the source `functions.json`

This file is a working note recording a systematic comparison of the
[duckdb.org](https://duckdb.org) function documentation
(`duckdb-web`, `docs/current/sql/functions/*.md`, site version **DuckDB 1.5.5**)
against two references:

* the catalog of a running DuckDB 1.5.5 engine
  (`duckdb_functions()`, Python package 1.5.5,
  which statically bundles the `core_functions`, `icu` and `json` extensions), and
* the `functions.json` metadata in the DuckDB 1.5.5 sources
  (59 files at tag `v1.5.5`, commit `d8cdaa33fd`),
  which is what both `dd` and the generated parts of the website consume.

Method: all 30 pages under `docs/current/sql/functions/` were parsed into
structured entries (594 detail blocks, 830 summary-table rows),
joined against the catalog (901 distinct `main`-schema function names),
the JSON metadata (436 flattened entries) and the `dd` package
(1103 generated stubs, 1221 documented names including aliases,
after [#28](https://github.com/cynkra/dd/pull/28) added the functions of
DuckDB's core extensions; section 5 records the before/after).
Every runnable inline example (461 of them) was executed on DuckDB 1.5.5
with the same rendering the site generator uses
(`SELECT ⟨example⟩::VARCHAR`, time zone `America/Los_Angeles`)
and compared against the documented **Result**.

Headline numbers: of the 755 scalar/aggregate/macro names in the catalog,
496 appear on the `sql/functions/` pages;
the rest are operators, collation entries, or functions documented elsewhere —
minus the genuine gaps listed below.
Of the 461 executed examples, 387 reproduce exactly,
30 mismatch (about a third of those substantively),
and 31 error (mostly examples that legitimately need context;
five are genuine bugs).

Only 5 of the 30 pages (`array`, `blob`, `lambda`, `list`, `text`)
are generated by `scripts/generate_sql_function_docs.py`;
everything else is hand-maintained, and that is where nearly all drift lives.

## 1. Factually wrong on the website (engine-verified)

* **`aggregates.md`, statistical aggregates `regr_sxx` / `regr_syy` / `regr_sxy`.**
  All three are described as "The sample variance/covariance,
  which includes Bessel's bias correction",
  and `regr_sxy` and `covar_samp` list each other as **Alias(es)**.
  They are not aliases and not sample statistics:
  on `(y, x) = (1,2), (2,4), (4,5)`,
  `covar_samp` returns 2.167 while `regr_sxy` returns 4.333,
  and `regr_sxx` returns 4.667 while `var_samp(x)` returns 2.333.
  These functions return the *sums* of squared deviations / deviation products
  (`n * var_pop`, `n * covar_pop`), as in PostgreSQL.
  (The source JSON's own text for `regr_sxy`,
  "Returns the population covariance of input values",
  is also wrong — it is the population covariance *times n*;
  see section 4.)

* **`datepart.md`, `timezone_hour(date)` / `timezone_minute(date)` / `timezone(date)`.**
  Documented as functions of `DATE` with runnable examples such as
  `timezone_hour(DATE '1992-02-15')` and result `0`.
  On 1.5.5 all three raise
  `Not implemented Error: "date" units "timezone_hour" not recognized`.
  They work for `TIMESTAMP`/`TIMESTAMPTZ`/`TIME`, not for `DATE`.

* **`datepart.md`, `timezone(date)` detail block.**
  Says "Time zone offset in minutes";
  the parts table further up the same page says seconds, and seconds is correct
  (`timezone(TIMESTAMPTZ '1992-07-15 20:30:00')` in `America/Los_Angeles`
  returns `-25200`).

* **`utility.md`, `count_if(x)`.**
  Description: "rows contribute 1 if `x` is `true` or a non-zero number";
  example `count_if(42)` with result `1`.
  On 1.5.5 the example throws
  `Binder Error: No function matches count_if(INTEGER)` —
  the function only accepts `BOOLEAN`.
  The catalog description is
  "Counts the total number of TRUE values for a boolean column".
  (It is also an aggregate, listed among scalar utility functions,
  and its canonical spelling on `aggregates.md` is `countif`.)

* **`struct.md`, `struct_extract_at`.**
  Example `struct_extract_at({'v1': 10, 'v2': 20, 'v3': 3}, 20)` with result `20`;
  index 20 is out of range and the example errors.
  The intended index is `2`.

* **`timestamptz.md`, `make_timestamptz(microseconds)`.**
  Example `make_timestamptz(1667810584123456)` documents
  `2022-11-07 16:43:04.123456-08`;
  the engine returns `2022-11-07 00:43:04.123456-08`
  (the documented value is off by 16 hours —
  1667810584123456 µs is 08:43:04 UTC).

* **`map.md`, `map_extract` detail block.**
  Says the function returns "`NULL` if the key is not contained in the map";
  the engine returns an *empty list*
  (`map_extract(MAP {'k': 5}, 'missing')` → `[]`).
  The summary-table row on the same page has it right.
  (`map_extract_value` is the variant that returns `NULL`.)

* **`union.md`, `union.tag` (dot notation).**
  Example `(union_value(k := 'hello')).k` documents result `string`;
  the actual result is `hello`.

* **`list.md`, `list_intersect`** (an auto-generated page):
  example documents `[3, 2]`, the 1.5.5 engine returns `[2, 3]` —
  the page was generated with a different engine build and is stale
  for the version the site labels "current".

* **`utility.md`, `stats(5)`**:
  documented result `'[Min: 5, Max: 5][Has Null: false]'` is stale;
  1.5.5 returns `[Min: 5, Max: 5][Has Null: false, Has No Null: true][Approx Unique: 1]`.

## 2. Missing from the website's function pages

Functions present in the 1.5.5 catalog (and documented in `dd`)
that appear nowhere on the `sql/functions/` pages,
and — unless noted — nowhere else under `docs/current/`:

* **`sinh`, `cosh`, `tanh`** — completely undocumented,
  while their inverses `asinh`, `acosh`, `atanh` have full entries on `numeric.md`.
  This is the most visible gap.
* **`nanosecond(ts)`** — `datepart.md` documents `microsecond` and `millisecond`
  but not the `nanosecond` extraction function (present since 1.1,
  returns sub-minute nanoseconds).
* **`mod(x, y)`** — only the `%` operator is documented;
  the function spelling is absent from `numeric.md`.
* **two-argument `log(b, x)`** — `numeric.md` documents only `log(x)` (base 10);
  the engine and JSON also provide `log(b, x)` (`log(2, 8)` → `3.0`).
* **Geometry**: `geometry.md` omits 8 of the new built-in spatial functions:
  `st_asbinary`, `st_astext`, `st_aswkb`, `st_aswkt`,
  `st_crs`, `st_setcrs`, `st_geomfromwkb`, `st_intersects_extent`.
* **`VARIANT` functions**: `variant_typeof` and `variant_extract`
  appear only on the `VARIANT` data-type page;
  `variant_normalize`, `variant_bytes_to_variant`,
  `variant_to_parquet_variant` are undocumented.
* **Aggregate variants**: `arg_max_nulls_last` / `arg_min_nulls_last`
  ("Finds the rows with N maximum vals, including nulls") are undocumented;
  `aggregates.md` documents only `arg_max_null` (2-argument).
* **Window alias `rank_dense`** — `window_functions.md` names it as an alias of
  `dense_rank` in prose, but it isn't in that page's function list
  (harmless; noted for alias metadata, section 4).
* **System/utility scalars**: `current_connection_id`, `current_query_id`,
  `current_transaction_id`, `in_search_path`, `get_block_size`,
  `struct_keys`, `remap_struct`, `normalized_interval`.
* **Logging**: `write_log` and `parse_duckdb_log_message`
  are mentioned nowhere except a passing reference in the configuration overview.
* **`pg`-compatibility macros**: `current_user`, `current_role`,
  `session_user`, `user`.
* **JSON**: `json_pretty` and `json_serialize_plan` are absent even from
  `data/json/json_functions.md`
  (the other ~40 `json_*` functions are documented there — by design,
  since JSON is an extension; not counted as gaps here).
* Deliberately excluded from the gap list:
  `sum_no_overflow` (catalog says "Internal only"),
  `count_star` (internal name for `count(*)`),
  `combine` / `finalize` / `get_type` / `make_type` / `vector_type` /
  `cast_to_type` (aggregate-state and typing helpers;
  `cast_to_type` is documented on the `CAST` page),
  `getvariable` (documented under `SET VARIABLE`),
  `switch` (documented under `CASE`),
  and the 135 `icu_collate_*` entries backing `COLLATE`.

## 3. Classification and style inconsistencies on the website

* **Table functions presented as scalar entries** on `utility.md`:
  `query`, `query_table`, `glob`, `repeat_row`, `read_text`, `read_blob`,
  `checkpoint`, `force_checkpoint` are documented in the same
  Description/Example/Result format as scalar functions,
  but every one of those examples fails unless called in a `FROM` clause.
  (`dd` and the catalog classify them as table/pragma functions.)
* **Summary table vs. detail block drift** on hand-maintained pages
  (26 cases; most benign, the substantive ones are
  `map_extract` and `timezone(date)` in section 1,
  plus `date.md` `date_trunc` where only the detail block carries the
  "always returns a `TIMESTAMP`" caveat — which is correct on 1.5.5 —
  and `bitstring.md` `bitstring_agg` whose two texts describe
  different behaviors).
* **`interval.md` results** are stylized (`INTERVAL 5 DAY`)
  rather than rendered engine output (`5 days`) —
  unlike every other page, which shows engine output.
* **Trailing semicolons inside inline `Example` cells** on a handful of entries
  (`map.md` `map_extract_value`; `timestamp.md` `epoch`;
  `timestamptz.md` `epoch_ns`, `epoch_us`; `utility.md` `create_sort_key`),
  which breaks the "example is a bare expression" convention
  used everywhere else (and by the site generator).
* **`timestamptz.md` `to_timestamp`** result is rendered in `+00`
  while the rest of the page renders in `America/Los_Angeles` (`-07`/`-08`).
* `regular_expressions.md` says "Three rows:" where the generator convention is
  "Multiple rows:", and duplicates `regexp_*` entries that `text.md` also carries
  (with slightly different texts, e.g. the optional-`options` sentence).

## 4. Where the JSON / catalog metadata (and therefore `dd`) is behind the website

The hand-edited pages fixed things the source metadata still gets wrong.
These belong upstream in `duckdb`'s `functions.json`,
which would fix `dd` and the generated pages at the same time:

* **`histogram`, `histogram(arg, boundaries)`, `histogram_exact`**:
  JSON/catalog say "Returns a LIST of STRUCTs with the fields bucket and count";
  the engine returns a `MAP` (`typeof(histogram(x))` → `MAP(BIGINT, UBIGINT)`).
  The website says `MAP` and is right; `dd` currently shows the stale text.
* **`make_timestamp_ms`**: JSON description says
  "The timestamp for the given *microseconds* since the epoch" —
  copy-paste from the `_us` variant; should be milliseconds.
* **`regr_sxy`**: JSON "population covariance" —
  actually `n * covar_pop` (see section 1).
* **`hamming`**: JSON typo "The Hamming distance between *to* strings"
  (the website fixed this to "two").
* **Alias links missing in the metadata**:
  the website documents alias relationships that exist only as
  independent macros in the catalog, with no `alias_of` and no JSON `aliases`,
  so `dd` renders them as unrelated pages:
  `geomean` ↔ `geometric_mean`, `wavg` ↔ `weighted_avg`,
  `list_append` ↔ `array_append` / `array_push_back`,
  `list_prepend` ↔ `array_prepend`, `list_reverse` ↔ `array_reverse`,
  `today` ↔ `current_date`, `get_current_time` ↔ `current_time`,
  `dense_rank` ↔ `rank_dense`, `format_bytes` ↔ `pg_size_pretty`.
* Roughly 260 of the 594 web detail entries carry descriptions that are
  materially richer than the JSON one-liners
  (e.g. `quantile_cont`/`quantile_disc`, `time_bucket`, `bar`,
  the window functions, `arg_min`/`arg_max` with `n`).
  That prose only exists on the website;
  ports of it into `functions.json` would benefit every consumer
  (see `proposals/duckdb-argument-descriptions.md` for the same argument
  applied to parameters).

## 5. `dd` vs. the website: resolved by dd#28, and what it surfaced

An earlier revision of this note listed the ICU and JSON extension functions
(`today`, `current_date`, `make_timestamptz`, `get_current_time`,
`icu_sort_key`, the `->>` operator, ~40 `json_*` functions, …)
as missing from `dd`,
because the R `duckdb` package does not bundle those extensions.
[dd#28](https://github.com/cynkra/dd/pull/28) closed this:
`scripts/generate.R` now installs and loads every core extension
before snapshotting `duckdb_functions()`,
and attributes each function to the extension that provides it.
`dd` grew from 745 to 1221 documented names
(+476 functions across 23 core extensions:
spatial 164, icu 144, json 43, ducklake 22, iceberg 16, delta 11, …).

After the change, the direction of the comparison flips:

* The only names on the website's function pages that `dd` does not document
  are the expected parser/CLI constructs with no catalog entry:
  `coalesce`, `if`, `ifnull`, `extract`, `grouping`, `getenv`.
  Every catalog-backed function on those pages now has a `dd` page.
* Of the bare-engine catalog (901 `main`-schema names),
  the only ones absent from `dd` are the Python-binding internals
  `pandas_scan` and `python_map_function` (correctly absent from R)
  and the deliberately dropped `__internal*` helpers.

Sweeping *all* of `docs/current/` (not just the function pages)
for the 1220 names `dd` now documents surfaces new website-side gaps —
user-facing extension functions with no mention anywhere on duckdb.org:

* **spatial** (`core_extensions/spatial/functions.md` omits them):
  `ST_ClosestPoint`, `ST_CoverageClean`, `ST_Expand`, `ST_InteriorRingN`,
  `ST_Snap`, `ST_SymDifference`,
  plus `shapefile_meta` and `pragma_rtree_index_info`.
* **json**: `json_pretty`, `json_serialize_plan` (also noted in section 2).
* **sqlite_scanner**: `sqlite_query`
  (the page documents attaching and `sqlite_scan`, not the query passthrough).
* **ducklake**: 14 maintenance/table functions
  (`ducklake_add_data_files`, `ducklake_commit`, `ducklake_list_files`, …) —
  partly by design, since DuckLake documents itself on
  [ducklake.select](https://ducklake.select),
  but duckdb.org's DuckLake page does not say so per function.
* Classes reasonably absent from the website, listed for completeness:
  the 135 `icu_collate_*` entries backing `COLLATE`,
  the `pg_catalog` compatibility macros
  (`has_*_privilege`, `pg_*_is_visible`, `format_type`, …),
  and extension debug/test helpers
  (`delta_filter_pushdown_log`, `check_peg_parser`,
  `mysql_debug_execution_plan`, the `quack` demo extension, …).
  That last class raises a `dd`-side open question:
  whether such debug helpers should be filtered out of `dd`
  the way `__internal*` already is.

## 7. Suggested next steps

1. Upstream (`duckdb/duckdb-web`): fix the section-1 errors —
   they are all one-line patches with engine-verified corrections.
2. Upstream (`duckdb/duckdb-web`): add the missing entries of section 2,
   starting with `sinh`/`cosh`/`tanh`, `nanosecond`, `mod`, `log(b, x)`
   and the eight `st_*` functions.
3. Upstream (`duckdb/duckdb`): fix the `functions.json` texts of section 4
   (histogram → MAP, `make_timestamp_ms`, `regr_sxy`, `hamming` typo)
   and add the missing `aliases` links —
   both `dd` and the generated pages pick these up automatically.
4. ~~`dd`: load `icu` and `json` in `scripts/generate.R`~~
   Done in [dd#28](https://github.com/cynkra/dd/pull/28),
   which went further and loads *all* core extensions.
   Follow-ups surfaced by it: the website-side extension gaps of section 5,
   and the open question whether `dd` should filter extension debug helpers.
5. Longer term: extend `generate_sql_function_docs.py` beyond its current
   5 pages, or add a CI check that executes documented examples —
   every error in section 1 would have been caught mechanically.
